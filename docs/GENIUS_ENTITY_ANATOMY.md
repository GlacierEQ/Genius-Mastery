# Genius Entity Anatomy

## Purpose

This is the kernel-up anatomy shared by the Genius family. A capability is not a label or a prompt. It is a real path from desired reality through prerequisites, intelligence, interfaces, execution, verification, and retained gain.

The family-level question is:

> What must exist, be accessible, be compatible, be correctly represented, and successfully operate for this capability to become true in reality?

## Recursive law

Every high-level verb is decomposable until its leaves match executable primitives.

```text
GOAL
  -> required reality
  -> required states
  -> required actions
  -> required capabilities
  -> required resources/interfaces
  -> executable primitives
  -> observed effects
  -> verification
  -> retained gain
```

Every verified higher-order capability becomes a new composable object.

```text
Skill A + Skill B + integration -> Capability C
Capability C + Skill D + evidence -> Capability E
Capability E -> reusable input to the next composition
```

## Importance is contextual

Do not weight every detail equally. Each dependency is evaluated against the current mission for necessity, criticality, sensitivity, substitutability, downstream centrality, and improvement leverage.

A property can be irrelevant in one mission and decisive in another. A failed implementation does not equal a failed capability when an alternate route exists.

## Failure semantics

Prefer:

```text
OBSERVE -> CLASSIFY -> PRESERVE SUCCESS -> ROUTE -> REPAIR -> REVERIFY -> RECONCILE -> CONTINUE
```

A blocked state is scoped to the exact operation whose required dependency has no executable alternate route. It is not a global veto over unrelated working capability.

## Universal contract

Use:

- `schemas/capability.schema.json` for the machine-readable contract.
- `templates/CAPABILITY.yaml` as the human-editable starting point.

The template intentionally spans more layers than most individual capabilities need. Empty or irrelevant layers are valid. The point is to make them inspectable so a tiny hidden dependency cannot silently collapse a large mission.

## Core optimization question

For any mission, Genius should be able to answer:

1. What is actually required?
2. What already exists and works?
3. What is missing or degraded?
4. Which missing factor materially affects the mission?
5. What substitutes or alternate routes exist?
6. Which improvement produces the greatest propagated gain?
7. What evidence proves the resulting capability?
8. What new compositions become possible afterward?

That is the bridge from a skill collection to a vertically integrated entity.
